The problem we're solving

Chat with any LLM today and the conversation is a single straight line. That creates three real pains:

🧵 One timeline

To try a different approach you either edit-and-lose the old answer, or start a brand-new chat and lose all the context that got you there.

↩️ No real "undo"

"Go back to how it was 8 messages ago, but keep this other branch too" is impossible. Exploration is destructive.

🔍 No way to find a moment

Long chats become a wall of text. "Where were we discussing the pricing options?" means scrolling forever.

The idea, in one paragraph (git for chats)

You chat with the model linearly, exactly like ChatGPT. When you decide the conversation just reached a moment worth preserving, you type /cp [label] — that's a commit. It writes a checkpoint node to a tree, capturing all the messages since the previous checkpoint. Keep chatting. Commit again. If you ever want to explore a different direction, click a past checkpoint in the tree — that's checkout — and continue. Your next commit becomes a child of that checkpoint, forking the tree. Nothing is destroyed.

Key insight: you don't need any "checkpointing machinery." An append-only commit tree is the checkpoint system. That's exactly what a document database with graph traversal expresses cleanly — which is why MongoDB fits so naturally (see below).

How the commit tree grows

Each session gets a short prefix (s1). Each checkpoint gets an id like s1-3 and a label. HEAD marks where the next commit will attach.

active path (root → HEAD) other branches (preserved)

s1-2 is a straight commit after s1-1. Then you clicked s1-1 (checkout) and chatted a different direction; the next /cp created s1-3 as a sibling of s1-2. You came back to s1-2, kept going, committed s1-4. s1-3 is untouched.

What one checkpoint looks like

{
  _id:           ObjectId("…"),
  sessionId:     ObjectId("…"),
  shortId:       "s1-2",              // human-friendly, per-session
  parentId:      ObjectId("…s1-1"),   // the tree edge
  depth:         2,
  label:         "pricing",           // from /cp pricing
  summary:       "Discussed pricing tiers vs. usage-based …",
  deltaMessages: [                    // the messages between s1-1 and s1-2
    { role: "user",      content: "compare tiered vs usage-based pricing" },
    { role: "assistant", content: "Tiered gives predictable revenue …" },
    { role: "user",      content: "which is better for early stage?" },
    { role: "assistant", content: "Usage-based reduces buyer friction …" }
  ],
  embedding:     [0.013, -0.221, …]    // vector on summary for semantic search
}

Storing only the delta per commit (like git) keeps checkpoints small. Reconstructing the full conversation for any node = one $graphLookup from that node back to root, then concatenate deltas in depth order.

The user flow

  1. Start a session. A root checkpoint s1-0 is created; HEAD = root. The screen splits into commit tree (left) and conversation (right).
  2. Chat linearly. Type prompts, hit Enter. Messages accumulate in the conversation panel and are tracked as uncommitted — a working-directory chip on the top bar shows the count.
  3. Commit with /cp [label]. One API call writes a checkpoint node to the tree under HEAD, embeds a summary, and clears the uncommitted state. HEAD moves to the new node.
  4. Keep chatting → commit again. Straight-line commits stack: s1-1 → s1-2 → …. Context between commits keeps growing normally.
  5. Fork by clicking. Click any earlier checkpoint in the tree. HEAD jumps there. Chat, then /cp — that new commit becomes a child of the older node. The path you left behind stays intact.
  6. Jump by meaning. Type "where did we discuss pricing" in the search box. Atlas Vector Search returns matching checkpoints with scores; click one to check it out.
  7. Switch models anytime. Provider dropdown flips between Ollama (local) and OpenAI (paste a key). Same UI, same tree.

Why MongoDB is the right choice

This is not "a database bolted onto an AI app." The core data structure is a commit tree, and the core queries are tree-traversal and vector-similarity — both native to Atlas.

1 · The document model is the tree

Each checkpoint is a document with a parentId. No rigid schema, no join tables — the branching shape maps 1:1 onto documents. Adding a commit is a single insert.

2 · $graphLookup reconstructs any path

Rebuilding the conversation for any checkpoint (root → node) is one aggregation that walks parentId. No N+1 queries, no application-side loop. That path becomes the exact context we send to the model.

3 · Atlas Vector Search = navigate by meaning

Each checkpoint's summary is embedded on commit. $vectorSearch filtered to the session gives ranked "where did we discuss X" jumps. The database that stores the tree also searches it — no separate vector store to sync.

4 · One store for structure + semantics

Tree links, message deltas, and vectors live in the same collection. One query language, one connection, one thing to deploy. And MongoDB owns Voyage AI, so best-in-class embeddings are a first-class swap.

The one-liner for judges: "The chat is a commit graph of documents; $graphLookup reconstructs any past state in a single query and Atlas Vector Search makes a dense history navigable by meaning."
